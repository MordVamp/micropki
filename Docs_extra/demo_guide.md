# Руководство по демонстрации MicroPKI

Данный документ описывает процесс демонстрации работы инфраструктуры открытых ключей (MicroPKI). В корне проекта находится скрипт `demo.sh`, который автоматически выполняет полный цикл операций: от создания изолированного корневого центра сертификации до выпуска клиентских сертификатов и проверки журнала аудита.

## Запуск демонстрации

Так как скрипт написан на bash, для его запуска на Windows вы можете использовать **Git Bash**, **WSL** (Windows Subsystem for Linux) или **MSYS2**. 

Убедитесь, что у вас установлен язык **Go**, и он добавлен в переменные среды (`PATH`).

**Команда для запуска (в терминале Git Bash или WSL):**
```bash
./demo.sh
```

*(Если вы столкнулись с ошибкой доступа, выполните `chmod +x demo.sh` перед запуском).*

## Что происходит внутри (Пошаговый разбор `demo.sh`)

Скрипт пошагово симулирует реальную эксплуатацию защищенного Удостоверяющего Центра (PKI).

### Шаг 1. Инициализация Root CA (Изолированная среда)
Скрипт создает изолированный Root CA. 
- Создается директория `./pki_root`.
- Создается директория `./pki_root_usb`, эмулирующая внешний USB-накопитель (флешку).
- Генерируется корневой ключ. Он **надежно шифруется** (PBKDF2 + ChaCha20-Poly1305) паролем и сохраняется **только на USB-накопитель**.

### Шаг 2. Выпуск Intermediate CA (Разделение архитектуры)
- Создается промежуточный центр сертификации (Intermediate CA).
- Для подписи его сертификата скрипт обращается к ключу Root CA, который находится на эмулированном USB-накопителе.
- Данные Intermediate CA сохраняются в совершенно другую директорию — `./pki` со своей отдельной базой данных (`micropki.db`).
- **Симуляция Air-Gapped / Офлайн:** Сразу после подписания сертификата скрипт "отключает" USB-флешку (переименовывая директорию в `pki_root_usb_offline`), демонстрируя, что ключ Root CA физически отключен от сети.

### Шаг 3. Инфраструктурные сертификаты
- Выпускается специализированный сертификат для службы OCSP-ответчика, чтобы другие узлы могли доверять его ответам.
- Генерируется первый пустой список отозванных сертификатов (CRL).

### Шаг 4. Запуск серверов (в фоне)
- Запускается **HTTP-сервер Репозитория** на порту `8080`. Сервер защищен иерархическим алгоритмом ограничения запросов (TCP HTB Rate Limiting).
- Запускается **OCSP-Ответчик** на порту `8081` для проверки статуса сертификатов в реальном времени.

### Шаг 5. Работа клиента (Генерация и подпись)
- Клиентская сторона локально генерирует свой закрытый ключ и CSR (Запрос на сертификат) для домена `localhost`.
- Удостоверяющий Центр (Intermediate) подписывает CSR, применяя шаблон `server`, и выпускает сертификат.

### Шаг 6. Криптографическая проверка
- С помощью утилиты `openssl` выполняется жесткая проверка всей цепочки доверия: от корневого сертификата (Root CA) до выпущенного сертификата `localhost`.

### Шаг 7. Пример использования (Подпись кода / Code Signing)
- Выпускается отдельный сертификат для подписи кода (шаблон `code_signing`).
- Создается текстовый файл, который подписывается этим сертификатом.
- Происходит успешная криптографическая проверка подписи (Verify).

### Шаг 8. Отзыв (Revocation) и Аудит
- Клиентский сертификат (`localhost`) отзывается по серийному номеру (с причиной `keyCompromise`).
- Имитируется компрометация сертификата Code Signing.
- Вызывается команда верификации журнала аудита. Система проверяет криптографическую целостность `Hashchain` и проверяет `HMAC-подпись` (Non-repudiation) для каждой записи лога. Это гарантирует, что историю аудита невозможно было подделать или переписать.

---

## Завершение работы
В конце демонстрации скрипт автоматически:
1. Выполняет поиск событий "компрометации ключа" в журнале аудита.
2. Корректно завершает работу фоновых серверов Репозитория и OCSP (`kill $REPO_PID $OCSP_PID`).

Если вы хотите запустить скрипт заново, он автоматически удалит сгенерированные файлы (`pki`, `pki_root`, `secrets`, `out`) перед новым циклом.
