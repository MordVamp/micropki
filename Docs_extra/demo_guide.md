# Руководство по Демонстрации MicroPKI и Материалы для Презентации

В этом документе собраны все необходимые материалы для успешной защиты проекта: тексты для слайдов, ключевые команды для работы со скомпилированным бинарником `micropki`, а также пошаговое руководство по проведению демонстрации полного цикла работы инфраструктуры открытых ключей.

---

## Часть 1. Текст для слайдов презентации

Эти тезисы можно использовать как текстовое сопровождение (речь) или прямо перенести на слайды для защиты архитектурных решений, принятых в проекте (в соответствии со стандартами из консультации).

### Слайд 1: Защита и Изоляция Корневого Удостоверяющего Центра (Root CA)
* **Проблема:** Хранение закрытого ключа Root CA в обычной базе данных или на горячем сервере критически уязвимо.
* **Решение в MicroPKI:** 
  * Закрытый ключ корневого УЦ шифруется с помощью AES-256 (GCM) / ChaCha20-Poly1305.
  * Ключ шифрования генерируется надежным алгоритмом PBKDF2 из сложного пароля.
  * Физическая изоляция: зашифрованный контейнер хранится на отдельном носителе (например, USB-накопителе, симулируемом директорией `--usb-path`).
  * Volatile Lifecycle: Ключ расшифровывается *только* в оперативной памяти на момент выпуска Intermediate-сертификата и немедленно удаляется из памяти после операции.

### Слайд 2: Архитектурное Разделение (Root CA vs Intermediate CA)
* **Проблема:** Компрометация сервера, выпускающего конечные сертификаты, может привести к краже корневого ключа.
* **Решение в MicroPKI:** 
  * Жесткое логическое и физическое разделение Root и Intermediate CA.
  * Root CA не подключен к сети и не использует СУБД для хранения выпущенных сертификатов. Он используется 1 раз в 10 лет для подписи Intermediate CA.
  * База данных SQLite используется исключительно на уровне Intermediate CA для трекинга конечных сертификатов (End-Entity) и OCSP-ответов.

### Слайд 3: Безопасность и Неотказуемость Журнала Аудита (Audit Log)
* **Проблема:** При компрометации сервера злоумышленник может перезаписать логи аудита и скрыть факт несанкционированного выпуска сертификатов.
* **Решение в MicroPKI:** 
  * Внедрен криптографический журнал операций на базе структуры **Hashchain**. Каждая новая запись хеширует содержимое предыдущей (по принципу блокчейна).
  * **Неотказуемость (Non-repudiation):** Записи дополнительно защищаются цифровой подписью (HMAC), что делает невозможным незаметную подмену истории (Tampering), даже если злоумышленник получит полный доступ к файловой системе БД.

### Слайд 4: Защита от Сетевых Перегрузок (Rate Limiting)
* **Проблема:** Сервисы проверки статуса сертификатов (OCSP / Repository) уязвимы к атакам отказа в обслуживании (DoS).
* **Решение в MicroPKI:** 
  * Реализован собственный алгоритм *Hierarchical Token Bucket* на уровне прослушивателя TCP-сокетов.
  * Ограничение частоты запросов происходит до того, как запрос будет передан на прикладной уровень HTTP (или TLS), что эффективно отсекает паразитный трафик и обеспечивает QoS (Quality of Service).

## Часть 2. Ключевые команды для работы с бинарником (standalone)

Скомпилированный бинарный файл лежит в директории `bin/micropki` (или `bin/micropki.exe`). Ниже приведены основные команды, которые можно использовать в консоли для ручной работы:

### 1. Создание Корневого CA (Root CA)
```bash
./bin/micropki ca init \
    --subject "CN=MicroPKI Root CA,O=Defense" \
    --key-type rsa --key-size 4096 \
    --passphrase-file ./root_pass.txt \
    --out-dir ./pki_root \
    --usb-path ./pki_usb
```
*(Обратите внимание: ключ будет сохранен в папку `pki_usb`, симулируя съемный носитель).*

### 2. Выпуск Промежуточного CA (Intermediate CA)
```bash
./bin/micropki ca issue-intermediate \
    --subject "CN=MicroPKI Intermediate CA" \
    --root-cert ./pki_root/certs/ca.cert.pem \
    --root-key ./pki_usb/ca.key.pem \
    --root-pass-file ./root_pass.txt \
    --passphrase-file ./inter_pass.txt \
    --out-dir ./pki \
    --db-path ./pki/micropki.db
```

### 3. Выпуск Конечного Сертификата (End-Entity Server)
```bash
# Генерация CSR
./bin/micropki client gen-csr --subject "CN=web.local" --out-key ./web.key --out-csr ./web.csr

# Подпись (выпуск)
./bin/micropki ca issue-cert \
    --ca-cert ./pki/certs/intermediate.cert.pem \
    --ca-key ./pki/private/intermediate.key.pem \
    --ca-pass-file ./inter_pass.txt \
    --template server \
    --subject "CN=web.local" \
    --csr ./web.csr \
    --out-dir ./pki/certs \
    --db-path ./pki/micropki.db
```

### 4. Отзыв Сертификата
```bash
./bin/micropki ca revoke <СЕРИЙНЫЙ_НОМЕР> --reason keyCompromise --db-path ./pki/micropki.db
```

### 5. Проверка Криптографического Аудита
```bash
./bin/micropki audit verify --log-file ./pki/audit/audit.log
```

## Часть 3. Проведение автоматизированного демо (Скрипт `demo.sh`)

Скрипт `demo.sh`, находящийся в корне репозитория, полностью автоматизирует весь цикл работы PKI от развертывания до тестирования OCSP, CRL и компрометации.

### Как запустить демо в Windows (Git Bash):
1. Откройте **Git Bash** (не обычную командную строку или PowerShell, так как скрипт написан для bash).
2. Перейдите в папку проекта:
   ```bash
   cd /c/rust/micropki
   ```
3. Запустите скрипт:
   ```bash
   bash demo.sh
   ```

### Что покажет демо:
1. **Clean & Build:** Очистка старых файлов и компиляция свежего бинарника.
2. **Изоляция:** Выпуск Root CA (ключ кладется в `pki_root_usb`), выпуск Intermediate CA, после чего USB-накопитель программно "отключается" (`mv ./pki_root_usb ./pki_root_usb_offline`), доказывая независимость Root CA от остальной инфраструктуры.
3. **Запуск Сервисов:** Старт репозитория сертификатов и OCSP-респондера в фоне.
4. **Политики Безопасности:** Попытка выпустить сертификат со слабым ключом (RSA 1024) — система его отвергнет. Затем успешный выпуск сертификата (RSA 2048).
5. **TLS:** Поднятие тестового HTTPS сервера с выпущенным сертификатом и успешное подключение к нему (verify PASS).
6. **Code Signing:** Выпуск сертификата для подписи кода, создание подписи файла и ее успешная проверка (openssl dgst).
7. **Отзыв (Revocation):** Отзыв сертификата, регенерация CRL. Повторная попытка подключиться к HTTPS серверу — завершится с ошибкой (verify FAIL), так как клиент проверит CRL.
8. **Аудит (Audit Log):** Проверка целостности hashchain журнала, симуляция компрометации через `ca compromise` и извлечение соответствующих событий из лога (`audit query`).
